# Engineering Choices

## Decision 1: Detection Model — YOLOv8 over RT-DETR and MediaPipe

### Options considered
- YOLOv8n
- YOLOv8s
- RT-DETR
- MediaPipe Pose

### What AI suggested
Claude suggested RT-DETR because of stronger performance on partially occluded persons in crowded retail scenes. ChatGPT suggested MediaPipe as a lightweight alternative.

### What I chose and why
I selected YOLOv8s for the final implementation.

RT-DETR provides strong detection accuracy but increases inference latency and deployment complexity for CPU-only execution inside Docker. The challenge evaluation environment prioritizes portability and simple deployment over benchmark accuracy.

MediaPipe was rejected because it is primarily optimized for pose estimation rather than general retail visitor detection.

YOLOv8s provided sufficiently accurate person detection while maintaining acceptable CPU inference performance and straightforward integration with OpenCV-based processing.

The final decision prioritized:
- deployment simplicity
- Docker compatibility
- stable CPU inference
- easier debugging during development

rather than maximizing detection benchmark scores.

# Decision 2: Event Schema Design — JSONL over Kafka and Direct Database Writes

### Options considered
- Direct database writes
- Kafka event streaming
- JSONL event files

### What AI suggested
Claude suggested Kafka-based streaming for a more scalable event-driven architecture.

### What I chose and why
I selected JSONL event files as the primary pipeline output and replay mechanism.

Kafka introduces additional operational complexity:
- broker setup
- topic management
- consumer synchronization
- Docker orchestration overhead

For a single-store prototype and hackathon environment, this complexity was unnecessary.

JSONL provides several advantages:
- replayable event streams
- easy debugging
- append-only architecture
- simple schema validation
- lightweight ingestion into APIs

The schema was intentionally designed to remain future-compatible with streaming systems like Kafka if the system scales to multi-store deployment later.

This approach balanced:
- production-style event architecture
- fast implementation
- operational simplicity

while remaining aligned with the challenge deliverables.

# Decision 3: Storage Architecture — In-Memory Store over PostgreSQL

### Options considered
- Python in-memory dictionary
- SQLite
- PostgreSQL

### What AI suggested
ChatGPT recommended PostgreSQL for stronger production readiness and persistence guarantees.

### What I chose and why
I selected an in-memory event store combined with JSONL persistence.

PostgreSQL would improve persistence and concurrency handling, but it also introduces:
- additional Docker containers
- schema migrations
- volume configuration
- higher setup complexity for evaluators

The challenge prioritizes:
- quick startup
- reproducibility
- API correctness
- minimal operational friction

Using an in-memory structure keeps the API extremely lightweight and allows the project to run immediately after `docker compose up`.

Persistent replayability is still preserved through the JSONL event log generated by the pipeline.

For larger multi-store deployments, PostgreSQL would become necessary for:
- concurrent ingestion
- historical analytics
- long-term persistence
- query scalability

However, for this prototype, deployment simplicity and evaluation reliability were prioritized over horizontal scalability.

# Decision 4: Tracking Strategy — Lightweight Tracking over DeepSORT and ByteTrack

### Options considered
- DeepSORT
- ByteTrack
- Lightweight centroid tracking

### What AI suggested
Claude recommended ByteTrack because of stronger identity consistency under occlusion and crowded retail movement.

### What I chose and why
I implemented lightweight centroid-style tracking for the prototype.

ByteTrack and DeepSORT improve cross-frame identity consistency, but they also introduce:
- additional tuning complexity
- dependency overhead
- higher compute requirements
- more difficult debugging during evaluation

The challenge focuses heavily on:
- event quality
- analytics correctness
- production explainability

rather than state-of-the-art re-identification accuracy.

The lightweight tracking approach was easier to:
- debug
- explain
- run reliably on CPU-only systems
- integrate into the event generation pipeline

This tradeoff intentionally prioritized stable event generation and deployment simplicity over advanced tracking accuracy.
